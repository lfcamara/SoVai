# A release is a manual version bump, a lint gate, and an entry saying why

Cutting a release means three things done by hand: bump `version` in `.claude-plugin/plugin.json`, run the reference linter, and write a dated entry in `CHANGELOG.md` explaining why the change was worth making. Nothing is generated and nothing is automated.

The version number is load-bearing rather than decorative because Claude Code surfaces it: an installed user sees that a new version exists and updates to it, and that is the only channel this plugin has to them. It also means a bump changes the process running inside their sessions without them having asked, which is precisely what the number has to communicate — the difference between a rewording and a workflow that no longer behaves the way they learned it. Semantic versioning is the shared convention for saying that in one field, so the three parts are defined in the changelog header rather than left to taste, and a plugin whose product is process gets its own reading of them: patch is a fix, minor is a new capability, major is the workflow changing shape.

The entry carries the **rationale**, not the change. A diff is a permanent record of what happened and a terrible record of why, and why is the half that decays — it lives in the head of whoever made the decision, for a few weeks. Someone returning to a skill six months later needs the argument that produced it, because without that argument the safe move is always to leave everything alone, which is how a collection turns to sediment. It is the same reason this plugin keeps ADRs at all; the changelog is the release-shaped view of the same discipline.

The linter belongs inside the release step rather than in someone's memory, because of the specific way this plugin fails. Its surface is cross-references — skills naming skills, ADRs citing agents, a manifest declaring every skill path — written as bare names that nothing validates. A dead one raises no error. It silently does not happen, in a session belonging to someone who has no way to know the reference was ever meant to resolve, and who will reasonably conclude the plugin does not work rather than that one name went stale. Shipping is the last moment that failure is cheap to catch, so the check sits there: `skills/knowledge/lint-references/lint.sh`, exit 0 or the release stops.

**Generated changelogs were rejected.** Deriving entries from commit messages produces an accurate list of what changed, which is the half already recoverable from the diff, and drops the half that is not. Conventional-commit tooling would additionally push the rationale into commit subjects, where it has to be written before the change is finished and cannot be revised once the release makes sense as a whole. The cost of writing entries by hand is real — it is work, and a forgotten entry leaves a hole nothing will fill later — and it is the right cost while there is one maintainer. Changesets and comparable release tooling are deferred on the same reasoning rather than dismissed.

**No versioning at all was rejected.** It works perfectly for a single user who is also the author, and stops working at the second install: an installed user with no version and no changelog cannot tell whether their sessions changed, cannot report a problem against anything in particular, and has no reason to update. That failure is not gradual. It arrives whole, on the day someone else runs the plugin.
