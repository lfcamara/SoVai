# Review has a goal axis, as a skill rather than an agent

`review` dispatches a sixth axis, `goal-review`, which asks whether the outcome the ticket existed for now holds: is the change merged into the branch it was meant to reach, is the flag or rollout that gates it actually switched on where the goal has to hold, and does the shipped work cover the ticket's full stated scope.

The gap is structural rather than a matter of thoroughness. The five existing axes all judge the diff — `code-review` how it is written, `spec-review` whether it is the right thing, `test-review` whether it is covered, `security-review` what it exposes, `migration-review` what happens when it runs. A change that is unmerged, merged but held behind a warn-only mode or an unset flag, or two thirds of its ticket looks identical from inside the diff to one that is none of those things. The information simply is not in the artifact the five axes read, so no amount of sharpening them reaches it. That is the same argument ADR-0007 used to justify `spec-review` against the other four, applied one level out: `spec-review` reads the requirements the diff was built against, and this axis reads the world the requirements were about.

The axis is a skill dispatched to the existing read-only `reviewer`, not a new agent. ADR-0006 splits agents by execution mode rather than job title: what changes an outcome is which tools an agent holds, which skill it must follow, and what counts as done — and this axis needs the same tools and the same read-only constraint as every other axis. A `goal-reviewer` agent would be a job title with nothing behind it, and it would put the axis's rubric in a file the dispatcher cannot vary per run, where every other axis carries its rubric in a skill the brief points at.

Folding these checks into `spec-review` was considered and rejected. It would give one skill two different reference points — the spec on one side, the deployed world on the other — and the merged report would let a clean spec verdict absorb a live goal failure, which is exactly the masking that keeping axes unranked and unmerged exists to prevent. The two also differ in what makes them answerable: `spec-review` needs only a diff and a spec, where this axis needs a pull request whose state can be read.

Leaving it to `wrap-up`'s merge preconditions was the other rejected option. Those preconditions are real and stay where they are, but they run after the user has already been asked to approve the PR. A precondition that fires at that point turns an approval the user gave in good faith into a question they should never have been asked, and ADR-0008 is explicit that approval given on a false premise is the failure to design against. Enforcement state, in particular, outlives the merge entirely — a merged, unenforced change satisfies every merge precondition there is.

Because merge and enforcement state cannot be read off a working tree, the axis is conditional: it runs when a ticket names an outcome and a pull request exists to read state from. Within a run it separates facts from findings — an open draft PR on a ticket still in progress is consistent, and only a state that contradicts a claim of done becomes a finding. Without that split the axis would report "not merged" on every mid-implementation review and be trained away as noise.
