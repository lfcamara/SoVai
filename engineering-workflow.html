Engineering Workflow

How work moves from an idea someone had in the shower to code merged into main — twelve stages, three cadences, one rule about who is allowed to decide what, and four hooks that stop the rest of it being optional.

The pipeline

Everything above to-roadmap runs once. Everything below runs once per phase, and the last four once per ticket — always at the moment that work begins, never in advance. Detail planned against a codebase that will have moved is detail that gets thrown away.

The ticket lifecycle

Every transition belongs to the orchestrator. A subagent that dies mid-task would leave its ticket stranded with nothing alive to reconcile it — and an implementer marking its own work Done bypasses the state that exists to have something else validate first.

The five review axes

Independent skills, dispatched as parallel read-only agents and reported per axis, never merged or reranked — a change can pass one and fail another, and a merged list lets a clean axis bury a failing one under a wash of minor style notes.

AxisThe question it answersSelected when
code-reviewIs it written well? Repo standards plus 12 Fowler smells — where refactoring livesAlways
spec-reviewIs it the right thing? Missing requirements, scope creep, wrong implementations, scope deferred without saying soA spec exists to hold the diff to
test-reviewWould the tests fail on a real regression?Always
security-reviewWhat does it expose? A finding must name a concrete path to harmThe diff touches a security surface
migration-reviewReversibility, destructive operations, backfills — failure mode here is data lossThe diff touches a schema or a migration

Scope quietly deferred belongs to spec-review, as a fourth finding type beside missing, unasked and implemented wrong. A sixth axis carried that question for a while, reading the merge and enforcement state a diff cannot show; it was removed once wrap-up owned the merge gate and the phase's exit criteria it had been reporting on separately, leaving covered scope as the only question it still held alone.

The ticket promised three things and the diff carries two, all of it well written. Work the PR or the ticket names as deferred is a fact, and often a sound call — the finding is silence about it, because that is what reaches the merge looking complete.

Delegation

The main session orchestrates and holds the decisions; execution goes to subagents. A subagent starts cold — none of the conversation reaches it — and it cannot ask a question. So the brief carries six things.

FieldWhat it carries
OutcomeWhat is true when this is done — a result, not stepsmakes the work possible
SkillWhich skill to run, by name
InputsAbsolute paths, and the facts it cannot look up
DoneCheckable criteria, with the command that proves themmakes it safe
FenceWhat it must not touch
ReportThe specific facts to return

If you cannot write the brief, you do not understand the task well enough to delegate it.

Three agents, split by execution mode

implementer
Writes and verifies
reviewer
Reads only, so findings stay findings
screen-verifier
Observes a running system through a browser, and fixes nothing

Not job titles. A role label barely changes a capable model's behaviour, while tool grants and completion criteria change everything — and the third sits on that axis rather than across it, since observing a running system is a third execution mode beside writes and reads-only. Widening reviewer's grant instead was the leading alternative and was rejected because a browser can click: an agent able to submit a form or press a delete control is not read-only against the running system, however read-only it stays against the repo.

The trade is stated rather than hidden — no fixed tool allowlist can name browser tooling whose names vary by environment, so screen-verifier is read-only by discipline where reviewer is read-only by construction. The boundary with the test suite is clean: ui-testing writes the tests for a screen after it is built, derived from the effort's wireframes, and screen-verifier observes that screen running and writes none.

Two standing rules all three carry, and every brief repeats: an unsettled decision goes back rather than being resolved locally, and the report is bound by verify-before-claiming — done means each criterion was checked against a run, with the output that settles it. Each agent definition names that skill rather than restating it, so the standard has one owner and sharpening it stays one edit.

What makes it non-optional

Everything above describes a process. Until these hooks existed, all of it was advisory — a skill the agent could reach for, or not, with nothing downstream noticing the difference. Two of the plugin's own decisions turned out to assume a mechanism nobody had built: that the planning pipeline auto-continues, and that TDD is mandatory for non-UI logic.

  1. SessionStart — the bootstrapThree things and nothing else: the orchestration mandate, the statement that invoking the matching skill is mandatory rather than optional, and one line per block of the pipeline. The mandate lives here because a plugin does not ship its CLAUDE.md — that file governs work on SoVai itself and never loads in a consuming project, which is the only place the rule has anything to govern. It stays short as a constraint rather than a preference: every line loads into every session, forever.
  2. The pre-edit gateFires on the first edit of each class per session. A production-logic path is pointed at tdd before the edit lands; a UI path is pointed at ui-testing for once the screen is built, and told not to open with a test.
  3. The phase trackerRecords that tdd was entered. The pre-edit gate reads it to switch a production edit into Green-minimal — telling a session mid-Green to go and fetch a skill it is already running pollutes Green with exactly the work tdd defers to code-review. The Stop gate reads it as the evidence that TDD happened at all.
  4. The Stop gateRefuses to end a session that edited production logic without ever invoking tdd. Honest about being a heuristic: it detects TDD skipped entirely, never red-before-green ordering, which nothing observable at the end of a session can establish. UI is never gated here — it is the deliberate exception, so the gate reads only the production signal and a UI-only session ends clean. Three escape paths, and it prints the exact override command for legitimate non-TDD work.

Enforcement survives delegation. Hooks fire inside subagents, and the session id is identical in a subagent and in the session that dispatched it — subagents are told apart by a separate agent id. So a production edit made inside an implementer writes the same signal the main session's Stop gate reads once that run is over. Had the id been per-agent the layer would have been decorative: the orchestrator writes almost no production code itself.

What was deliberately not built

No hook forces delegation. Counting the orchestrator's own edits and complaining would have been easy, and wrong: mandatory TDD is a property of the work, while whether to delegate is a judgement about context economy — a two-line fix costs more to brief than to make. Only the first kind of rule belongs in a gate.

Evidence before the claim

A hook can observe that an edit happened, that a skill was entered, that a session is ending. It cannot observe whether the sentence about to be written carries evidence — and the failure that matters most is a report asserting more than its run supports, or with no run behind it at all. So that one is a rule the agent holds while it writes — verify-before-claiming, binding every done, fixed, passing and working, and binding a subagent exactly as it binds the orchestrator — a binding that travels in the brief and in each agent's own definition rather than being assumed.

Run the check that would contradict the claim, and show what it said. Where no command stands behind a claim, name what you could not verify.

One always-on rule rather than a criterion inside each skill, because a rule living in a skill is silent for exactly the runs where no skill was invoked — the quick fix, the ad-hoc edit, the question that turned into a change — which are the runs where an unverified done is likeliest. Where the subagent boundary compresses the log, what crosses is still the command, its result, and the lines that failed.

Per-project configuration

Three facts cannot be discovered from a repo. Where its tickets go — the tracker and whatever fields name a destination in it, under a tracker key, with local markdown as the floor that always works. What makes a fresh checkout runnable — a git worktree carries tracked files and nothing else, so the commands that restore the .env, the node_modules and the build cache are listed under worktreeSetup, and delegate runs them before dispatching an implementer in. And what a file is: the fact the hooks run on. All three live in one sovai.config.json at the project root, found by walking up from the edited file.

KeyExample patternsWhat it means
productionLogicsrc/**, lib/**TDD is mandatory — both gates read this
uisrc/components/**, src/app/**The deliberate exception: covered after it is built, never gated at Stop
tests*.test.*, test/**Gated by nothing

Three lists of shell globs, not a stack enum: src/components is UI in one project and a component library dense with logic in the next, and the only party that knows is the project. Precedence runs tests, then ui, then productionLogic, so a UI path nested under a production path wins and nobody writes exclusions. Onboarding is a one-file drop, never a change to the plugin — and because the file sits at the root and is found by ancestry, worktrees and clones inherit it for free.

Everything fails open, so a project with no config is not gated at all. No config, or a malformed one, classifies nothing: no reminders, and a Stop gate that never fires. The direction is chosen — under-gating costs a missed reminder, while over-gating costs a developer who cannot finish a session, and a hook that breaks work over its own configuration gets uninstalled, taking every rule it was carrying with it.

The vault, and the loop that feeds itself

The project's docs/ folder is an Obsidian vault. Documents link each other with wikilinks, and those links are what make it a graph rather than a pile. Filenames carry the effort — checkout-flow — Spec.md, not spec.md — because the graph shows the note's name and nothing else.

Severity decides obligation

SeverityWhat it meansObligation
criticalData loss, a security breach, or a broken production pathAlways fixed
highIncorrect behaviour a user meets, or a broken guarantee the code claimsAlways fixed
mediumA real defect with bounded blast radius, or a standard breach that costs laterOnly if you say so
lowWorth fixing, cheap to leaveOnly if you say so

The boundary between high and medium is the one that carries weight — it is where a fix stops being optional. wrap-up will not merge with a critical or high finding unresolved, no matter how firmly the PR was approved.

A finding is a defect caught. A cause that repeats is a hole in the process — and the two are not the same thing.

So every finding records why it was not prevented, and the review record persists in the vault. This is the one part of the loop that cannot be reconstructed later: without a written cause, recurrence is invisible and the vault accumulates incidents instead of lessons. Causes name the gap — “the spec never said which seam” — not the moment or the person. “Missed it” is unmatchable and unfixable.

harden turns recurrence into a rule

  1. Group by cause, not symptomTwo findings that look unrelated can share one hole in the process. Clusters are weighted by severity — recurrence at critical earns an amendment sooner than recurrence at low.
  2. Find the ownerOne test: what single artifact, present when the defect was introduced, would have stopped it? A missing rule points at the axis; a loose completion criterion at the skill that let it pass as done; a permitted action at the agent definition.
  3. Sharpen, don't appendWhere an existing rule was almost right, it gets rewritten rather than joined by a second one nearby. A rule added per incident is sediment — and is how the original rule stayed weak enough to miss this.
  4. Propose, don't applyA skill change alters every future run, so nothing lands from a pattern you have not seen. Runs periodically, never per review — one occurrence is not a pattern.

It runs in the SoVai repo, where the skills live, reading vaults from whichever projects you point it at. A cause appearing once in each of three projects is invisible from inside any one of them — and that is the pattern most worth catching.

lint-references checks it still holds together

harden amends the plugin from what reviews found; lint-references checks that what came out the other side still resolves. The cross-references here are almost all bare names in prose — a skill naming a skill, an ADR citing an agent — and nothing reads them back: not the filesystem, not Claude Code, not any other tool. A rename leaves the old name reading exactly as live as the day it worked, and a dead one raises no error. It silently does not happen, in a session belonging to someone with no way to know the reference was ever meant to resolve.

Five checks: bare names, the manifest's declared paths, the reverse direction (on disk but undeclared, which never loads), relative links, and the hook wiring. It refuses to print clean on a run that checked nothing — a linter that scans zero references must fail loud. It is step 2 of cutting a release, which is the last moment a dead reference is cheap to catch; each release and the reasoning behind it live in CHANGELOG.md.

Debug

A bug gets no special path. It gets diagnosed, and the diagnosis produces a ticket that enters the same flow as everything else — implemented under TDD, reviewed, merged on your approval.

  1. EvidenceGet an instance of the bug, preferring to go and get it — the database, the browser, the logs — over accepting the report. A reported symptom is a secondhand account.
  2. Build the feedback loopOne command, already run once, that is red-capable, deterministic, fast and agent-runnable. Reaching for a hypothesis before that command exists is the exact failure the discipline prevents.
  3. Reproduce and minimiseCut until every remaining element is load-bearing — removing any one of them turns the loop green.
  4. HypothesiseThree to five, ranked, each falsifiable with a stated prediction. A hypothesis with no prediction is a vibe.
  5. Test them in parallelOne hypothesis per agent. They are independent by construction, and one agent testing several in sequence anchors on whichever it tried first.
  6. File the ticketEvidence, the reproduction command, the minimised repro, the root cause, the seam analysis, and what would have prevented the bug.
